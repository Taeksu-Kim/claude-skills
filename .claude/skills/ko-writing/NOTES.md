# ko-writing 노트

## 설계
- 하는 일: Claude가 한국어 글(메일·메신저·보고서·안내·소개 글)을 쓸 때 AI 티 없이 쓰고, 이미 있는 글을 고칠 때도 같은 기준으로 고친다.
  근거: 사용자 요청 "한국어 말투로 작성하거나 바꿔주는 스킬" + 방향 확인 답 "Claude가 글을 쓸 때 기준" (2026-11-18).
- 쓰는 사람: Claude 자신 — 다른 스킬(SNS 소개 글·논문 글 스킬·보고서·메일 초안)이 한국어 본문을 쓸 때 참조. 사용자가 "AI 티 빼줘"라고 직접 부를 때도.
  `가정:` 붙여넣은 글 고치기는 부차 용도 (요청 문장에 "바꿔주는"이 있어서 넣음, 방향 답에서는 고르지 않음).
- 말투 기준: 장르별 일반 기본값 + 사용자 샘플이 있으면 샘플 우선 (방향 확인 답). 받아온 원문의 하우스 스타일은 범용 규칙에서 뺀다.
- 성공 기준: 사실·수치·말의 세기는 그대로이면서, 읽는 사람이 "AI가 쓴 것 같다"고 지목할 지점이 사라짐 (방향 확인 답).
  점수로 판정하지 않는다 — 남은 지점 목록 + 원문 대비 바뀐 곳 (메모리 no-numeric-rubrics).
- 부르는 때: 한국어 산문을 쓰거나 고칠 때. 코드 주석·커밋 메시지·짧은 채팅 답에는 `가정:` 쓰지 않음.
- 입력: 쓸 재료(사실·수치) 또는 고칠 글, 받는 곳(메일·메신저·문서·SNS), 선택: 사용자 말투 샘플.
- 결과: 글만 (다른 작업 안) / 고친 글 + 남은 지점·바뀐 곳 (직접 불렀을 때).
- 되돌리기 어려운 동작: 없음 (게시·전송은 부르는 쪽 스킬 몫).
- 실패 신호: 사용자가 결과 글을 다시 고침 / "AI 같다" 지적 / 사실·수치가 바뀜 / 다른 스킬의 말투 규칙과 부딪침.
- 재료: 받아온 humanize-ko 원문(작업본에만 둠) (MIT, im-not-ai·humanizer·stop-slop 기반).

### 검증 사례 (결과를 보기 전에 고정, 2026-11-18)
과제: 작성자의 문서 검색 도구 README를 읽고, 이 도구를 써 보라고 권하는 글을 사내 메신저
(서식 기호가 그대로 보이는 곳)로 동료 개발자에게 보낸다. 10~15줄 안팎.

통과 기준 — 회차마다 바꾸지 않는다:
- 규칙 준수 (예/아니오 + 증거)
  1. README에 없는 사실·수치·기능이 없다.
  2. 서식 기호(#, **, 표, 장식 이모지, → 화살표)가 없다 — 메신저라서.
  3. 강한 AI 패턴이 없다: "~에 있어", 이중 피동, 아무도 주장하지 않은 "A가 아니라 B", 문단 끝 한 줄 펀치, 챗봇 잔재,
     "다음과 같다"식 열거 도입, 광고 문구(혁신적·강력한·획기적·완벽한).
  4. 말의 세기: README가 단정하지 않은 것을 단정하지 않는다.
- 주 전문가(한국어 교열·편집자)가 보기에 좋은가
  5. 조건을 모르는 평가자가 "AI가 쓴 것 같다"고 짚는 지점이 스킬 없이보다 적고, 남은 지점이 어휘 하나 수준이다.
  6. 받는 동료가 첫 몇 줄에서 무엇을 왜 써 보라는지 알고, 바로 해 볼 수 있다 (흔한 수준: 기능 나열 / 닿아야 할 수준: 받는 사람의 일에 닿는 이득 하나 + 시작하는 법).

## 항목
**[F1] 재료를 다 옮김** — 입력: 검증 사례(README → 메신저 권유 글), 스킬 없이 · 증상: 기능 9개를 한 줄씩, 받는 사람의 이득·이유 없음 ·
원인: 받는 사람의 할 일을 정하지 않고 재료 순서대로 씀 · 조치: SKILL.md "쓸 때" 1·3 · 상태: 해결 (2회차 평가)

**[F2] 같은 틀의 줄** — 입력: 같음 · 증상: 12줄 중 83% 한 줄 한 문장, "~하고, ~합니다" 구조 반복 · 조치: "결" 줄바꿈 + check.py 줄 지표 · 상태: 해결 (2회차 평가)

**[F4] 같은 어미 연속** — 입력: SNS 소개 글 스킬로 쓴 게시 글 4편 · 증상: "~습니다." 4~7연속 · 조치: "결" 어미 + check.py · 상태: 해결 (2회차 평가)
