# 만들기 (무거운 경로) — 새 스킬, 판단 지점 2개 이상, 다른 스킬·동작의 바탕, 외부 동작 포함일 때 읽는다

경로는 skill-craft 폴더 기준.

## 절차형 — 정해진 단계를 묶는 스킬 (이 절만 읽고 끝. 아래 판단형 절차는 쓰지 않는다)
가치는 "단계를 빠뜨리지 않고, 환경 특유의 함정을 피하고, 끝에 맞게 됐는지 확인되는 것"에 있다. 전문가 모으기·축·루프는 하지 않는다.
1. 방향 확인: 하는 일 한 문장·쓰는 사람·끝났다를 무엇으로 아나 — 아래 판단형 1과 같은 방식, 한 번.
2. 재료는 사용자가 실제로 한 기록에서: 명령 기록·README·HANDOFF·이전 대화·`CLAUDE.md`. 단계는 기록의 명령·경로 그대로,
   기록에서 실패했던 곳은 함정 줄로. 기록에 없는 단계는 `가정:`으로 적고 보고에 낸다.
3. 쓴다: 단계(명령 그대로) / 단계마다 셀 수 있는 확인(종료 코드·파일 존재·건수 — "잘 됐나" 금지) / 외부 동작·삭제 앞 확인 /
   반복·재시도 상한 / 함정·관리 절 / description(사용자 말 그대로). 판단 지점이 섞이면 그 지점만 `guides/expertise.md` §4로.
4. 검증: 이 맥락에서 사례 하나를 실제로 끝까지 돌린다 (외부 동작은 적기만). 외부 동작·삭제가 있는 스킬만 새 맥락 1에게 스킬만 보고
   따라 하게 해 빠진 단계를 찾는다. 서브에이전트 상한은 대원칙 3.
5. `NOTES.md`는 [D] 몇 줄과 만든 과정 표(단계 ↔ 출처 기록)만.
보고: 만든 단계와 출처 기록, `가정:`, 검증에서 걸린 것. 결과가 "맞게 돌았는데 별로"로 갈리는 게 보이면 판단형으로 옮길지 판단 자료로 낸다.

## 판단형 — 아래 전부

## 목표
만든 스킬이 어려운 실제 사례에서 스킬 없을 때보다 결과를 낫게 바꾼다. 내용은 모델이 실제로 틀리는 곳·사용자 자료·
실패 기록에서 오고, 모델이 원래 하는 것(상식)은 넣지 않는다.

## 지킬 순서 — 이 넷만 순서를 지킨다 (너무 일찍 확정하는 것을 막는 순서다)
1. **방향 확인과 기준이 먼저**: 하는 일 한 문장·쓰는 사람·성공 기준을 입력에서 해석해 근거와 함께 확인받는다
   (설계에서 유일한 필수 확인 — 되돌리기 어려운 외부 동작 앞 확인은 대원칙 2대로 따로). 같은 때 검증 사례(어려운 실제
   사례 1개)와 통과 기준을 적는다 — 결과를 보기 전에.
2. **스킬 없이 먼저 돌린다**: 그 사례를 스킬 없이 한 번 (새 맥락 서브에이전트 1). 외부 동작(push·게시·전송·삭제)은
   하지 말고 "할 동작을 적기만" 하라고 지시한다 — 서브에이전트 안에서는 실행 직전 확인을 할 수 없다. 모델이 실제로 틀리는 곳이 스킬에
   넣을 내용의 0순위다 — 모델이 스스로 쓴 스킬은 효과가 없고 가치는 실제 교정·환경 특유의 함정에서 나온다는 보고가
   있다 (SkillsBench, `[인용·미확인]`). 틀리지 않는 부분은 스킬에 쓰지 않는다.
3. **모으기를 마친 뒤 고른다**: 사용자 자료와 2에서 틀린 곳부터, 사람(주 전문가·결과 판정자·인접) → 관심사 → 축 순서로
   넓게 모으고 (`guides/expertise.md`), 다 모은 뒤 고른다 — 모으면서 고르면 첫 후보가 굳고, 축을 먼저 정하면 사람이 빠진다. 고르기 검수: 남긴 규칙마다 출처가 있나 / 결과를 바꾸는 사례가 있나 / 상식 기준선과
   겹치지 않나 / 목표 방향과 맞나 / 사용자 자료와 부딪치는 것을 종류대로 처리했나 (사실·맥락·명시적 결정은 따름, 해 온 방식은
   판단 자료로 — `guides/expertise.md` §4 끝) → 아니면 다시 모으기로 (2회까지).
4. **쓴 뒤 전문성 루프 — 상한 2회차**: 스킬 있이 1의 사례를 돌려 2의 결과와 비교하고, 빈 곳이 있으면 고쳐 다시 돈다.
   - 기준은 1에서 고정한 것 그대로 (규칙 준수 + 주 전문가가 보기에 좋은가). 회차마다 바꾸지 않는다 — 바꾸면 기준 맞추기가 된다.
   - 회차 = 실행 1 + **새로 띄운** 조건 모르는 평가자 1. 지난 회차의 평가를 본 평가자는 그 평가에 끌린다. 같은 흐름의 자기 평가는 후하다.
   - 평가자는 빈 곳마다 실패 장면을 댄다 (못 대면 빈 곳이 아니다). 고칠 때 더하는 줄마다 출처나 실패 장면을 붙이고, 같은 회차에
     결과를 바꾸지 않는 줄을 뺄 수 있는지도 본다 — 돌수록 무거워지는 걸 막는다.
   - **강점 지키기**: 고치기 전에 평가자가 꼽은 지난 결과의 강점마다 스킬의 어느 줄에서 왔는지 적는다. 새 줄이 그 줄과 같은 자리를
     다투면("A **또는** B로 바꾼다"처럼 강점을 선택지로 만들면 하나가 빠진다) 대체하지 말고 둘 다 두거나, 못 두면 판단 자료로.
     다음 회차 평가자에게 그 강점이 남았는지도 묻는다 — 빈 곳만 채우며 돌면 처음 강점이 희석된다 (D29: episode-concept 2회차에서
     출처는 나아지고 첫 화면 그림 대비가 빠짐).
   - **나가는 조건** (하나라도): 실패 장면이 있는 빈 곳이 더 없음 / 있이·없이 차이가 지난 회차보다 커지지 않음(수렴 — 더 돌면 기준
     맞추기) / 2회차 끝. 남은 빈 곳은 판단 자료로. 서브에이전트 상한은 대원칙 3.
   - **3회차는 둘 다 맞을 때만, 확인받고**: 2회차 평가에 "사용자가 판단을 틀리게 함" 수준의 빈 곳이 **새로** 나옴 + 3회차는
     **다른 종류의 사례**(예: 읽기 화면이었으면 입력 화면)로 돈다. 같은 사례로 더 돌면 그 사례 전용 규칙이 쌓인다 —
     다른 사례에서도 걸리는 빈 곳만 일반 규칙이다. 예상 비용(회차당 [측정] 약 30만 토큰, D27)을 붙여 사용자에게 묻는다.
   - 서브에이전트에게 열지 말 파일(정답·NOTES·이전 결과)은 grep·find에서도 빼라고 경로를 적어 지시한다 (섞여 들어온 일이 있다, D23).
   - 루프는 모델과 출처가 닿는 데까지다 — 그 너머는 실제 사용의 [F]를 함정 줄로 넣는 바깥 고리가 맡는다 (`guides/history.md`, D26).

마지막에 **보고** — "만들었다"로 끝내지 않고 **무엇을 고려해 무엇이 들어갔는지**가 보이게 (사람이 결과를 믿을 근거):
1. 방향 (확인받은 것) · 2. 스킬 없이 돌렸을 때 틀린 곳 · 3. 고려한 것 — 축·전문가 집단·사용자 자료·실패 기록, 출처별 ·
4. 넣은 것 — 규칙 ↔ 출처 ↔ 결과를 바꾸는 사례 · 5. 뺀 것과 이유 (상식이라서 / 출처 없음 / 방향과 무관 / 사용자 자료와 충돌) ·
6. 남은 `가정:`·`가설:`(틀린 것만 표시해 달라고)·사전 부검 위험 · 7. 검증 결과 (있이/없이 차이) · 그 뒤 판단이 필요한 것만 대원칙 2의 판단 자료로.
4·5는 `NOTES.md` "만든 과정" 절에 표로 남긴다 (`guides/history.md`) — 대화가 끝나도 "왜 이 규칙이 있나"에 답할 수 있게.

## 제약 — 순서 없이, 쓰는 동안 지킨다
- **최신성**: 만드는 스킬의 결과가 지금 시점의 사실(뉴스·가격·정책·순위·모델·도구 버전)에 기대면, 그 스킬의 재료 단계에
  검색을 넣는다 — 무엇을 먼저(「주제어 + 최근 한 달」, 공식 발표), 상한, 결과에 집계·확인 날짜 표시. 스킬 파일에 박아 둔 숫자·목록은
  낡는다 — 박을 거면 날짜와 다시 찾을 조건을 붙인다 (episode-concept F14: 13일 전 더 큰 기사를 놓침, D30).
- **범위 기록**: 1 외의 범위(부르는 때·입력·결과·되돌리기 어려운 동작·실패 신호)는 칸마다 근거 또는 `가정:`으로
  새 스킬의 `NOTES.md` "설계" 절에 (`guides/history.md`). 위치 기본: `side_projects/.claude/skills/<이름>/`,
  한 프로젝트 전용이면 그 프로젝트의 `.claude/skills/`. 같은 이름의 스킬이 이미 있으면 다시 쓰기 전에
  `SKILL.md.bak-<날짜>` 사본 — 공용 폴더는 git이 없어 덮어쓰면 복구할 수 없다 (C2).
- **작업 순서 (대원칙 5)**: 만드는 스킬의 단계 순서를 정할 때 재료 → 틀, 구체 → 추상, 펼치기 → 좁히기, 판정 기준은 결과 앞.
  각도·구조·형식을 고르는 단계는 그 근거를 모으는 단계 뒤에 둔다. 출발점은 주 전문가가 실제로 일하는 순서다
  (`guides/expertise.md` §4) — 그 직업이 펼쳐 놓고 고르는 곳을 스킬이 단일안으로 건너뛰지 않게.
- **품질 기준**: 주 전문가의 판정 기준점(축을 만들었으면 축의 "닿아야 할 수준") 중 스킬 없이 돌린 결과가 닿지 못한 것은 해당
  판단 지점에 넣는다 — 실수 방지만 있으면 준수 검사가 될 뿐 결과의 질은 안 오른다 (D17). 1의 통과 기준에도 하나 이상
  (통과 기준을 1에서 미리 적을 때부터 "규칙을 지켰나"와 "주 전문가가 보기에 좋은가"를 둘 다 둔다).
  주 전문가의 **디테일 기준**(요소 단위 점검) 중 스킬 없이 돌린 결과물이 못 챙긴 것은 최종 결과 앞 검수 지점에 — 길면 점검표
  하위 파일, 잴 수 있는 건 스크립트 (`guides/expertise.md` §4·§6, D19).
- **판단 지점**: 스킬이 시킬 작업 중 입력만으로 답이 정해지지 않는 곳(방향·형식 결정, 자료 해석, 후보 선택,
  자기가 만든 것 평가, 범위 확대)마다 검수 지점을 둔다 — 질문·미리 적은 기준·통과 못 하면 돌아갈 곳 (대원칙 4).
  그 밖의 곳은 순서를 강제하지 않고 목표와 제약으로 쓴다.
- **구조 — 점진 로딩**: `SKILL.md`는 매번 통째로 읽히는 목차다. 항상 필요한 것(핵심 원칙·함정·경로)만 두고, 특정
  상황에서만 필요한 것은 하위 파일(`references/`·`guides/`)로 뺀다.
  - 하위 파일마다 **관찰 가능한 읽기 조건**을 `SKILL.md`에 적는다: "API가 non-200을 주면 `references/api-errors.md`",
    "입력이 PDF면 `references/pdf.md`", "검토 요청이면 `guides/review.md`". "필요하면 참고" 같은 조건은 쓰지 않는다 —
    모델이 판단할 수 없어 늘 읽거나 늘 안 읽는다.
  - 모든 하위 파일은 `SKILL.md`에서 한 단계로 연다. 하위 파일이 다른 하위 파일을 여는 사슬은 만들지 않는다.
  - 압축 뒤에는 앞부분만 남으니 `SKILL.md` 안에서도 가장 중요한 것을 맨 위에 둔다.
- **description**: 하는 일 + 다루는 상황을 넓게(사용자 말 그대로) + 비슷한 스킬과의 경계. 트리거되는 유일한 곳이다.
  "먼저 호출하라" 같은 강한 지시 대신 상황을 나열한다.
- **문장**: 태도 말("신중히") 대신 확인할 수 있는 동작 + 이유 한 줄. MUST·대문자 강조는 쓰지 않는다 (과잉 발동).
  "다시 확인하라" 같은 일반 재확인은 쓰지 않는다 (Opus 5부터 중복) — 확인은 검수 지점으로. 기계적 단계(세기·형식 검사)는
  스크립트로. (`../reference/PROMPTING.md` §3·§5)
- **예시**: 출력 형식에만 (영역이 다른 2개 + "핵심은 무엇", ✗는 무난한 답). 열린 작업에는 예시 대신 인터페이스(선택지·
  파라미터)와 실물 참고자료 경로 — 예시는 탐색 범위를 좁힌다.
- **강제 규칙**: 어기면 안 되는 것(게시·삭제 금지 등)은 문장보다 hook·권한 설정으로 (`update-config` 스킬). 스킬엔 이유만.
- **함정·관리 절**: "함정" 절(처음엔 2에서 틀린 곳)과 "관리" 절을 넣고 `NOTES.md`를 채운다 (`guides/history.md`).
- **사전 부검**: 검증 전에 "이 스킬대로 했다가 실패했다면 왜?" 3개 → 막을 수 있는 건 반영, 남는 건 `NOTES.md` [C].
- **완료 검수** (검증 전, 파일 글자에 대고): 하위 파일마다 관찰 가능한 읽기 조건이 있고 사슬이 없나 / `../reference/PROMPTING.md` §0 /
  description에 사용자 말 그대로가 있나 / 판단 지점마다 검수 지점이 있나 / 상한 없는 반복이 없나 / "함정"·"관리" 절이 있나 /
  다듬는 사이 목표 방향에서 벗어난 규칙이 없나 / 틀·결론 단계가 재료 단계보다 앞에 있지 않나 / 판단 지점에 품질 기준이 있나
  → 하나라도 아니면 해당 제약으로 돌아가 고친다 (2회까지).
