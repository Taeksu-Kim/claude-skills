# skill-craft — 스킬 만들기·고치기·검토

이 스킬로 만든 스킬은 다른 많은 동작의 바탕이 된다. 결함도 그대로 복제되므로 아래는 이 스킬 자신에도 적용한다.
**읽는 규칙**: 이 파일 → 아래 "규모 → 경로"와 "하위 파일" 표에서 조건이 맞는 파일만, 그때 (경로는 이 폴더 기준).
근거와 LLM 성질 전체는 `reference/PROMPTING.md`.

## 대원칙 1: 들은 만큼만 정한다
입력이 정하지 않은 것을 짐작으로 확정하지 않는다. 먼저 쓴 내용이 뒤의 판단을 끌고 가서, 나중에 정보가 와도
다시 판단하지 않고 덧대게 된다.
1. 정하기 전: "입력의 어디가 이걸 정하나?" 근거가 없으면 `가정:`으로 표시하고 진행한다.
   (확인 안 된 지식·암묵지는 `가설:` — 둘 다 보고에 목록으로 낸다.)
2. 새 정보가 오면: 초안에 끼워 넣지 말고, 그 정보에 기대는 결정을 전부 다시 판단한다.
3. 중간 판단(범위, `가정:`)은 파일에 남긴다 — 맥락이 요약돼도 다시 판단할 근거가 남는다.

되돌아보기는 일반적인 "다시 확인"이 아니라 판단 지점의 검수(대원칙 4)로 한다.

## 대원칙 2: 사람에게는 방향만 묻고, 나머지는 판단 자료로 낸다
사람 개입은 줄이되, 결과는 사람이 실제로 원하는 쪽에 닿게 한다.
| 구분 | 처리 |
|---|---|
| 방향·목적 (무엇을 위해, 누가 쓰나, 성공이 무엇인가) | 반드시 확인. 빈 질문 말고 "이렇게 이해했다 + 입력 근거"로 |
| 디테일 (구조·형식·단계·문구) | 묻지 않는다. 원칙대로 초안을 만들고 판단 자료를 붙인다 |
| 되돌리기 어려운 외부 동작 (게시·삭제·전송) | 실행 직전에 확인 |

**판단 자료** — 결정마다, 단계 중간에 끊지 말고 모아서 한 번에. 답이 없으면 추천안으로 진행한다.
- 추천안 — 이유 (입력의 어디서 왔나)
- 대안 — 결과를 실제로 바꾸는 축에서만. **"이런 경우면 이쪽이 낫다"** (갈리는 조건: 사람은 저울질보다 자기 상황 알아보기가 쉽다)
- 고르면 뒤에서 달라지는 것 / 추천이 기대는 `가정:`

예 — 핵심은 "짐작 확정 → 방향 확인 + `가정:`", "질문 → 초안 + 갈리는 조건". 영역·내용은 바뀌어도 된다.
- (A) "논문 정리 스킬 만들어 줘"
  ✗ 단계·출력 형식·말투까지 다 확정 → 뒤에 "LinkedIn용"을 들으면 형식 절만 고친다 (독자·길이·단계는 그대로)
  ✓ 방향("누가 읽나")만 확인, 형식은 `가정:` → "LinkedIn용"을 들으면 독자에 기대는 결정을 전부 다시 본다
- (B) 영수증을 읽는 식단 기록 스킬
  ✗ "수량 단위는 어떻게 할까요?"
  ✓ "g 단위로 썼습니다 (영양 계산에 바로 쓰임). 대안: 인분 — 외식 위주면 입력이 편해서 이쪽이 낫고, 대신 칼로리가 어림값이 됨"

## 대원칙 3: 비용에 상한을 둔다
이 스킬과, 이 스킬로 만드는 스킬 모두. 쓴 비용은 되돌릴 수 없다.
- 반복·재시도·병렬에는 횟수·개수 상한과 멈출 조건을 적는다. 상한에 닿으면 조용히 계속하지 말고 멈추고 보고한다.
- 비싼 동작(서브에이전트, 웹 검색, 유료 API·모델 호출, 큰 파일 전체 읽기, 긴 명령 출력)은 필요한 단계에서만, 개수를 정해서.
  읽기는 색인·목차 → 필요한 부분 순서. 큰 출력은 걸러서 본다.
- 유료 외부 호출은 기본 꺼짐(opt-in). 정한 상한을 넘겨야 하면 예상 비용을 붙여 실행 전에 확인받는다 (외부 동작과 같은 취급).
- 이 스킬의 상한 (재시도 포함해 센다): 절차형 만들기는 서브에이전트 0개(외부 동작·삭제가 있으면 "적기만" 하는 새 맥락 1). 무거운 경로는 사례 1개, 서브에이전트 5개까지 — 스킬 없이 1 + 전문성 루프
  2회차 × (있이 1 + 새로 띄운 평가자 1). 3회차(+2)는 `guides/create.md` 4의 조건이 맞고 사용자가 승인할 때만.
  가벼운 경로·검토는 서브에이전트 없이. 예외: 이 대화에서 만들거나 고친 스킬을
  검토할 때는 새 맥락 1개 (같은 흐름의 자기 검토는 후하다, C3).

## 대원칙 4: 판단 지점에는 검수 지점을 둔다
일반적인 "다시 확인하라"는 형식적 확인이 되고(자기 결과는 후하게 본다) Opus 5부터는 중복이다 (D12). 이 스킬과 만드는 스킬 모두,
**판단 지점 뒤 · 되돌리기 어렵거나 비싼 동작 앞 · 최종 결과 앞**에 검수 지점을 둔다. 모든 단계에 두지 않는다.
- 무엇을: 그 단계에서 실제로 나올 실패 모양마다 질문 하나 (사전 부검·전문가 암묵지·`NOTES.md` [F]에서). "잘 됐나?" 금지.
  **"목표 방향과 맞는가"는 항상 넣는다** — 빠지면 그럴듯하지만 목표와 반대인 규칙을 통과시킨다 (D10).
- 기준은 그 단계 결과를 만들기 **전에** 적는다 — 만든 뒤 적으면 결과에 맞춘 기준이 된다.
- 검수 기준은 배타적으로 나누지 않는다 — 한 결함이 여러 기준에 걸려도 된다. 하나에만 넣게 하면 놓친다 (D10).
- 무엇에 대: 입력·미리 적은 기준·실행 결과·파일 글자·사용자 자료. 쓰면서 한 생각에 대지 않는다. 셀 수 있는 건 스크립트로.
  일반 기준이 사용자 자료와 부딪치면: 사실·맥락·선호와 사용자가 명시적으로 정한 결정(`CLAUDE.md`·메모리·`NOTES.md` [D])은
  그대로 따르고, 해 온 방식·실력 판단은 스킬에 반영할지 판단 자료로 묻는다 (D10, D21).
- 통과 못 하면: 돌아갈 단계를 적고, 재시도는 2회까지. 넘으면 멈추고 판단 자료로 보고한다. 통과 증거 한 줄은 보고에 남긴다.

예 — 핵심은 "단계에 맞춘 질문 + 실패 시 돌아갈 곳". 영역은 바뀌어도 된다.
- ✗ "초안을 검토한 뒤 다음 단계로 넘어간다"
- ✓ (스킬 만들기) "검수: 남긴 규칙마다 출처가 있나 / 결과를 바꾸는 사례가 있나 / 목표 방향과 맞나 → 하나라도 아니면 모으기로"
- ✓ (영수증 읽기) "검수: 품목 금액 합 = 영수증 합계 (스크립트로) / 수량 0·음수 없음 → 다르면 해석 단계로, 2회 실패면 사람 확인"

## 대원칙 5: 순서가 검색을 정한다
먼저 쓴 것이 뒤에서 찾을 범위를 정한다 (대원칙 1과 같은 성질). 이 스킬의 절차와, 만드는 스킬의 작업 순서 모두:
- **재료가 틀보다 먼저**: 근거(입력·사용자 자료·실제 실패·성과 데이터)와 사람(실무자·결과를 판정하는 쪽)을 먼저 넓게 모으고,
  틀(축·구조·형식·템플릿)은 그 재료를 묶어서 뒤에 만든다. 틀을 먼저 쓰면 그 틀에 맞는 것만 찾는다 (D17).
- **구체가 추상보다 먼저**: 사례·데이터 → 규칙. 규칙을 먼저 쓰면 사례를 규칙에 맞춰 고른다.
- **펼치기가 좁히기보다 먼저**: 좁히는 결정은 방향 확인 직후 한 번, 나머지는 근거가 다 모인 뒤에.
- **예외 — 재는 틀은 앞에**: 판정 기준은 결과보다 먼저 적는다 (결과를 본 뒤 적으면 결과에 맞춰진다, 대원칙 4).
  만드는 틀은 뒤로, 재는 틀은 앞으로.
- **생각하는 순서와 보여 주는 순서는 다르다**: 만들 때는 근거 → 결론, 보고할 때는 결론 → 근거 (판단 자료는 추천이 맨 앞).
  사용자가 보여 주는 순서를 명시적으로 정했으면(예: "기준 먼저, 그다음 제안") 그걸 따른다 (D21·D24).
검수 (만드는 스킬의 순서를 정한 뒤): 틀·결론을 쓰는 단계가 그 재료를 모으는 단계보다 앞에 있지 않나 → 있으면 순서를 바꾼다.

## 함정 (실제로 겪은 것 — 겪을 때마다 한 줄, 자세한 건 `NOTES.md`)
- 모델 혼자 쓴 전문가 정의는 사용자 고유 규칙을 놓치고 일부는 반대 방향으로 쓴다 → 사용자 자료를 먼저 (D10)
- 검수 기준을 "한 결함은 한 기준에만"으로 나누면 결함을 놓친다 (D10)
- 서브에이전트 호출이 "hook이 입력을 바꿨다"며 한 번 거부될 수 있다 → 거부 메시지에 적힌 입력을 **글자 그대로** 한 번 다시 호출한다.
  hook이 붙이는 안내 블록을 내가 미리 붙여 보내면 두 번 들어가 다시 거부되고, 두 번째 거부 뒤에는 재시도할 수 없다 (F1·F4)
- 서브에이전트는 보고서 파일 쓰기가 막힐 수 있다 → 결과를 최종 응답 텍스트로 받게 지시하고, 저장은 이쪽에서 (F2)
- 축을 규칙 문서에서 먼저 뽑자 그 축에 맞는 사람만 찾아 실무자·결과 판정자가 빠지고, 정의한 수준은 `NOTES.md`에만
  남아 스킬이 품질 기준 없이 준수 검사만 했다 → 사람 먼저·축은 뒤, 수준은 판단 지점에 (D17)

## 규모 → 경로
| 요청 | 언제 | 읽을 것 |
|---|---|---|
| 고치기 (가벼운) | 기존 스킬의 규칙·문구 수정, 실패 신고("이상하게 동작해"·"안 불려") — 이번 수정이 바꾸는 판단 지점 0~1개 | 아래 "고치기" |
| 만들기 — 절차형 | 새 스킬인데 정해진 단계(명령·파일·순서)를 묶는 일이고, 결과가 "돌았나·나왔나·검사 통과"로 갈림 | `guides/create.md`의 "절차형" 절만 |
| 만들기 — 판단형 (무거운) | 새 스킬인데 같은 단계를 지켜도 결과의 질이 판단에 따라 갈림 (전문가가 보면 "맞는데 별로"가 있다) / 기존 스킬을 크게 다듬음(판단 지점 2개 이상을 바꿈 — 기존 `NOTES.md`·함정을 재료 ①로) / 외부 동작을 새로 넣음 | `guides/create.md` |
| 검토 | 기존 스킬을 봐 달라는 요청 | `guides/review.md` |

애매하면 가벼운 경로로 시작하고, 바꾸는 판단 지점이 2개 넘게 나오면 무거운 경로로 옮긴다 — 모든 수정을 무겁게 만들지 않는다.
절차형·판단형은 "이 결과를 두 사람이 다르게 평가할 수 있나"로 가른다 — 통과/실패뿐이면 절차형. 절차형에 판단 지점이 한두 개
섞이면 절차형으로 만들고 그 지점에만 전문성을 모은다 (스킬 전체를 무겁게 만들지 않는다, D28).

**하위 파일** — 모두 이 표에서 한 단계로 연다 (하위 파일이 다른 하위 파일을 여는 사슬을 만들지 않는다):
| 이럴 때 | 읽는다 |
|---|---|
| 만들기의 "모으기"(전문성)에 들어설 때, 검토에서 "전문가"·"전문성" 질문을 볼 때 (§3~§6) | `guides/expertise.md` |
| expertise §4에서 사람마다 관점·기준·방법을 쓸 때 (깊이의 기준 — 모방하지 않는다) | `guides/expertise-example.md` |
| `NOTES.md`를 새로 만들 때, [F]·[D]·변경 줄을 쓸 때, 스킬에 "함정"·"관리" 절을 넣을 때, 검토 대상에 `NOTES.md`가 있어 관리·추적 질문을 볼 때 | `guides/history.md` |
| 스킬 파일의 문장을 새로 쓰거나 고칠 때, 검토에서 "글" 질문을 볼 때 — §0 점검표 (근거 표는 §0이 가리킬 때만) | `reference/PROMPTING.md` |

## 고치기 (가벼운 경로)
1. 실패 신고면 먼저 재현: 사용자 말 그대로를 입력으로 무엇이 일어났는지 적는다. "안 불림"이면 description을 사용자 말과
   대조하고 설명 예산(항목당 1,536자에서 잘림, `PROMPTING.md` §5)을 본다.
2. 대상의 `NOTES.md` 색인을 읽는다 — 바꾸려는 것이 기존 결정 [D]·실패 [F]와 부딪치나.
3. 고친다 (크게 다시 쓰면 먼저 `SKILL.md.bak-<날짜>` 사본 — git 없음, C2). 고친 규칙에 기대던 다른 단계도 다시 판단한다 (대원칙 1-2).
4. 검수: 1의 재현 입력(또는 고친 계기)으로 다시 확인했나 / 목표 방향과 맞나 → 아니면 3으로 (2회까지).
5. `NOTES.md`에 변경 한 줄, 실패가 계기면 [F]와 함정 줄도 (`guides/history.md`). `NOTES.md`가 없으면 이때 만든다.

## 관리 (이 스킬 자신)
실패 신호: 만든 스킬을 사용자가 크게 고침 / 검증에서 있이·없이 차이가 없음 / 사용자가 판단 자료를 자주 뒤집음 /
"질문이 많다"·"너무 무겁다"는 지적. 걸리면 `NOTES.md`에 [F] 한 줄 (`guides/history.md`).
