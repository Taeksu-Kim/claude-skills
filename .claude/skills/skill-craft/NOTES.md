# skill-craft 노트

## 설계
- 하는 일: 스킬을 만들고·고치고·검토한다 — 판단을 단계로 나누고, 전문성을 바깥 출처로 채우고, 이력으로 자라게 한다 (사용자 방향, 2026-11-18)
- 쓰는 사람: 이 스킬을 따르는 Claude Code. 결과를 받는 사람은 사용자 (방향 확인·판단 자료 검토만)
- 성공 기준: 만든 스킬이 스킬 없이보다 결과가 낫다 (있이/없이 비교) · 사용자 개입이 방향 확인 + 판단 자료 검토로 끝난다 ·
  실패가 기록되어 규칙으로 돌아온다
- 부르는 때: description 참고 (만들기·고치기·검토)
- 입력: 사용자 요청·대화, 대상 스킬 파일·`NOTES.md`, 프로젝트 `CLAUDE.md`, `reference/PROMPTING.md`
- 결과: `SKILL.md`·하위 파일·`NOTES.md`, 판단 자료 형식의 보고
- 되돌리기 어려운 동작: 기존 스킬 덮어쓰기 (git 없음 → [C2])
- 실패 신호: `SKILL.md` "관리" 절

집단끼리 부딪치는 곳: 지식 공학자 "규칙을 줄여라" ↔ 체크리스트·품질 "검수 항목을 둬라" → 지금은 검수를 판단 지점에만(D9),
규칙은 결과를 바꾸는 사례가 있을 때만. 임상의 "감별 목록을 오래 유지" ↔ 참모 "결론 먼저" → 작업 중엔 `가정:`·대안 유지,
보고는 결론 먼저로 양립.
이 정의가 새로 시사하는 것 (✗·△, 아직 반영 안 함 — 판단 자료로 사용자에게): ① 규칙 수 관리 (규칙 하나 더하면 하나 빼기
검토) ② 작업 중 감별 목록 (판단 지점에서 대안 2~3개를 증거가 나올 때까지 유지) ③ 정기 재검증 (모델이 바뀌거나 오래 안
쓴 스킬은 있이/없이 재실행) ④ 판단 자료 선택지가 겹치지 않고 빠짐없는지 점검.

## 항목
**[D1] 들은 만큼만 정한다** — 이유: LLM 생성은 앞서 쓴 내용에 조건화된 검색이라 초반 짐작이 뒤를 좁힌다. 논문 "LLMs Get Lost
In Multi-Turn Conversation"(ICLR 2026)이 직접 받치는 것은 "입력에 없는 것을 짐작으로 확정하지 말라"까지 (사용자 논의) ·
버림: "신중한 판단"이라는 표현 — 태도라 실행되지 않고, 입력으로 돌아가는 동작이 빠짐 · 다시 볼 조건: 단계 분리가
결과를 개선하지 못한다는 검증 결과가 나오면

**[D2] 사람에게는 방향만** — 이유: 사용자 방향 "사람 개입은 최소화, 대신 원하는 결과가 나오도록 판단 자료(초안·대안·맥락·
장단점)를 준다" · 버림: "되돌리기 비싼 디테일은 선택지로 묻는다" — 질문이 많아지고 고르는 부담이 사용자에게 감 ·
다시 볼 조건: 사용자가 판단 자료를 자주 뒤집으면 (방향 해석이 약하다는 뜻 → 방향 확인 범위를 넓힐지)

**[D3] 전문성은 바깥 출처에서** — 이유: 출력은 최빈값(상식)으로 수렴, 역할 지시는 말투만 바꿈, "평범하지 말라"고 밀면
근거 없는 정교함을 지어냄 · 버림: "전문가처럼" 역할 지시 / 상식 초안 후 다듬기 (초안 근처에 머묾) · 다시 볼 조건:
있이/없이 검증에서 차이가 계속 없으면 출처 단계가 약한 것

**[D4] 전문가 집단·암묵지는 가설** — 이유: 암묵지는 정의상 글로 잘 안 남아서 모델이 내는 건 고정관념이기 쉬움 ·
버림: 모델이 정의한 암묵지를 사실로 쓰기 / 사용자 인터뷰 (개입 과다) → 가설 목록에 틀린 것만 표시 · 다시 볼 조건: 없음

**[D5] 이력 관리를 스킬 설계에** — 이유: LLM은 세션 간 경험이 쌓이지 않음, `NOTES.md`가 경험을 대신함. 실패를 기록해 규칙으로
돌리는 것이 전문가 특성 (사용자 제안) · 버림: git 이력 (공용 폴더가 git 아님) / 기록 절차 전체를 각 스킬에 (토큰) →
각 스킬엔 "관리" 절 한 줄, 형식은 `guides/history.md` · 다시 볼 조건: `NOTES.md`가 쌓이지 않거나 잡음만 쌓이면

**[D6] 규모별 경로** — 이유: 기반 스킬이라 무거운 절차가 모든 스킬로 복제될 위험 · 버림: 모든 스킬에 전 단계 ·
다시 볼 조건: 가벼운 경로로 만든 스킬에서 [F]가 반복되면 기준을 낮춤

**[D7] 본문·guides·PROMPTING 분리** — 이유: 본문은 매번 읽힘, 긴 맥락 중간은 덜 쓰임, 사람용 근거는 행동을 안 바꿈 ·
버림: 한 파일에 전부 · 다시 볼 조건: guides를 읽어야 할 때 안 읽는 [F]가 나오면 본문으로 올림

**[D8] 비용 상한** — 이유: 사용자 요청 (스킬이 과도한 비용을 쓰지 않게, 일반 안전 지침). 검증 서브에이전트 상한은 2 → 3
(실험에서 조건을 모르는 평가자를 따로 두는 것이 필요했음, D10) · 버림: 없음 ·
다시 볼 조건: 상한 때문에 검증이 부족했던 [F]가 나오면

**[D9] 구체적 검수 지점** — 이유: 사용자 지적 "일반적으로 진행이 아니라 특정 단계에서 검수". "넘어가기 전 대 본다"만으로는
자기 평가 편향 때문에 형식적 확인이 됨. 품질 관리의 정지점(hold point)과 같은 발상 · 버림: 모든 단계에 검수 (비용·무거움) ·
다시 볼 조건: 검수를 통과했는데 결과가 틀린 [F] → 그 지점의 질문을 고침

**[D10] 축 방식의 쓰임새** — 실험(2026-11-18, Opus 서브에이전트, 케이스당 1회, 조건을 모르는 평가자 1, 주제 하나):

- B: 축 미적용이 나음 — 심은 결함 7개 중 잡음 7 vs 5+일부 2. 원인: "한 결함은 한 축에만" 규칙이 판정 불가 형용사를
  상식으로만 분류, 목표 방향 축이 빠져 과장 유도 집단을 못 짚음. 대신 미적용 쪽 오탐이 1~2개 더 많음
- 공통: 사용자 고유 규칙 4개(비유 대조·비용 표기·각도 반복·AI 작성 공개)는 둘 다 못 찾고 2개는 반대로 씀.
  일반 검수 기준("독자 고정 금지")이 사용자 실제 규칙을 결함으로 판정
→ 정의는 축(개수 고정 없음, 추가 조건, 많으면 2단, 우선순위), 검수는 비배타 + "목표 방향" 상시 + 사용자 자료 우선,
  출처는 사용자 자료 필수. 축 개수를 열어 둔 것은 사용자 제안 (복잡한 일은 축이 여럿 필요)
· 버림: 축 2~4개 고정 (근거 없는 숫자) / 검수 기준에도 축 배타성 적용 · 다시 볼 조건: 재실험(케이스당 2~3회,

**[D29] 강점 지키기** — 이유: episode-concept 루프 2회차가 "비슷한 수준, 강점이 다름" — F12 반영 줄("정도 틀이나 그림 대비로")이 1회차 강점(첫 프레임 그림 대비)을 밀어냄. 사용자 "라운드 돌면서 처음 가졌던 강점이 희석될 수 있다는 거잖아" → 반영 승인 · 결정: create 4 루프에 고치기 전 강점 ↔ 줄 대조, 강점을 선택지로 바꾸는 줄 금지, 다음 평가자에게 강점 유지 질문 · 근거: `experiments/2026-11-18_expertise-test.md` 끝 절 · 버림: 고정 기준에 "지난 강점" 기준 추가(회차마다 기준이 바뀌면 기준 맞추기) — 평가 지시에 질문으로만 · 다시 볼 조건: 다음 루프에서 강점이 남았는데도 수렴만 반복되면 줄이 무게만 더하는지 본다

**[D30] 분야 자료 웹 검색** — 이유: 사용자 "스킬 만들 때 일반 지침·지식은 웹 검색도", 예로 다음에 만들 프롬프트 생성 스킬 · 결정: expertise ④를 조건부로 — ①~③ 뒤, 바뀌는 사실·기준 숫자·모델 지식이 얕은 분야일 때만, 공식 문서 먼저, 웹 검색 5 + 페이지 8, `[인용: URL, 날짜]`, 바뀌는 사실은 참고 파일에 날짜·다시 찾을 조건 · + 사용자 "최신성이 필요한 내용은 웹 검색 필요" → create 제약에 "최신성": 만드는 스킬이 현재 사실에 기대면 그 스킬의 재료 단계에 검색·상한·날짜 표시 · 버림: 늘 켜기(일반 베스트 프랙티스는 상식 기준선과 같고, 먼저 찾으면 사용자 방식을 덮음) / 옵션 플래그(요청 문구로 켜고 끄기로 대신) · 다시 볼 조건: 검색으로 넣은 줄이 검증에서 결과를 못 바꾸면 조건을 좁힌다

**[F1] 서브에이전트 호출 거부** — 입력: Agent 호출 (context-mode 플러그인 hook이 프롬프트 뒤에 안내문을 덧붙임) · 증상: "auto mode
