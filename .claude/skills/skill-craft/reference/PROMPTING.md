# LLM에 지침을 쓸 때 — 모델의 성질과 대응

스킬(`SKILL.md`)·시스템 프롬프트·에이전트 지침(`GUIDE.md` 등)을 쓰거나 검토할 때 본다. 모델을 부르는 법·서버·함정은 `LLM.md`.
일반론(명확하게 써라, 역할을 줘라 등)은 적지 않는다. **모델의 어떤 성질 때문에 지침이 어긋나는지**와 그 대응만 적는다.

> 출처 표기: **[인용·미확인]** 기억에 기댄 인용, 원문 대조 안 함 · **[관찰]** 이 저장소 작업에서 실제로 겪은 것 · 표기 없음 = 정리한 의견.
> 정리한 날 2026-11-18 (사용자와의 논의, `skill-craft` 스킬 설계 중).

## 0. 쓰기 전 점검 (요약)
- [ ] 입력이 정하지 않은 것을 확정하게 만드는 단계가 없나? 새 정보가 오면 덧대지 않고 다시 판단하게 되어 있나? (§1)
- [ ] 이 줄을 지워도 모델이 똑같이 할까? → 그렇다면 뺀다 (§2)
- [ ] 조건부 내용은 하위 파일로 빠졌고, 파일마다 관찰 가능한 읽기 조건이 본문에 있나? (§3 점진 로딩)
- [ ] 예시는 출력 형식에만 있나? 있다면 "핵심은 무엇, 나머지는 바뀌어도 됨"과 영역이 다른 2개인가? (§3)
- [ ] 태도 말("신중히", "꼼꼼히")과 강한 말("반드시", 대문자) 대신 확인할 수 있는 동작 + 이유인가? (§3)
- [ ] 단계마다 관찰 가능한 완료 증거가 있나? 자기 검토가 아니라 실행 결과·미리 적은 기준에 대 보나? (§4)
- [ ] 판단 지점 뒤에 단계에 맞춘 검수 질문·미리 적은 기준·실패 시 돌아갈 곳이 있나? (§1)
- [ ] 사람에게 묻는 건 방향·목적뿐인가? 디테일은 초안 + 판단 자료인가? (§1)
- [ ] 틀·결론을 쓰는 단계가 그 재료를 모으는 단계보다 앞에 있지 않나? 판정 기준은 결과 앞에 있나? (§1 순서)
- [ ] 반복·재시도·병렬·비싼 호출에 상한과 멈출 조건이 있나? (§4)

## 1. 앞에서 쓴 것이 뒤를 끌고 간다

생성은 앞서 쓴 내용을 조건으로 다음을 찾는 검색과 같다. 초반에 짐작으로 확정한 것이 뒤에서 찾을 범위를 좁히고,
나중에 정보가 와도 다시 판단하지 않고 **덧댄다**.
- 근거: 정보를 여러 턴에 나눠 주면 성능이 평균 39% 떨어지고, 한 번에 몰아 주면 거의 그대로. 원인 중 하나로 초반 짐작에
  기대는 습관을 꼽음 — "LLMs Get Lost In Multi-Turn Conversation" (ICLR 2026) [인용·미확인]
- 그래서 막을 것은 "길게 쓰기"가 아니라 **"입력에 없는 것을 짐작으로 확정하기"**다.
- 이 저장소에서: 도구 인자 스키마를 프롬프트에 안 주면 `from_ccy`→`from_currency`처럼 인자 이름을 지어냄 (`LLM.md` §4) [관찰]

**지침으로 쓰면** — 들은 만큼만 정한다:
1. 정하기 전: "입력의 어디가 이걸 정하나?" 근거가 없으면 `가정:`으로 표시하고 진행한다.
2. 새 정보가 오면: 초안에 끼워 넣지 말고 그 정보에 기대는 결정을 다시 판단한다.
3. 순서는 너무 일찍 확정하는 걸 막는 곳만 강제한다 (방향 → 기준 → 모으기 → 고르기). 나머지는 목표와 제약으로 (§5).

**순서가 검색을 정한다** — 같은 성질 때문에 단계의 순서가 곧 품질이다:
재료(근거·사람·사례·데이터)가 틀(축·구조·형식)보다 먼저 / 구체가 추상보다 먼저 / 펼치기가 좁히기보다 먼저.
예외로 **재는 틀(판정 기준)은 결과보다 먼저** — 결과를 본 뒤 적으면 결과에 맞춰진다. 생각하는 순서(근거 → 결론)와
보여 주는 순서(결론 → 근거)는 다르다. 실례: 축을 규칙 문서에서 먼저 뽑자 그 일을 직업으로 하는 실무자와 결과 판정자가 빠짐 (skill-craft D17).

`가정:` 표시는 같은 성질을 거꾸로 쓰는 장치다 — 짐작을 "임시"라고 써 두면 뒤의 생성도 그걸 임시로 다룬다.

**검수 지점** — 일반적인 "다시 확인하라"는 형식적 확인이 되고 (§4 자기 선호) Opus 5부터는 중복이다 (§5). 대신 판단 지점 뒤·비싸거나 되돌리기 어려운 동작 앞·최종 결과 앞에만:
그 단계의 실패 모양에 맞춘 질문 2~4개, 기준은 결과를 만들기 **전에** 적고, 입력·실행 결과·파일 글자에 대 보고,
통과 못 하면 돌아갈 단계와 재시도 상한. 품질 관리의 정지점(hold point)과 같은 발상.

**사람 관여** — 사람 개입은 줄이고, 결과는 사람이 원하는 쪽에 닿게 (사용자 방향, 2026-11-18):
| 구분 | 처리 |
|---|---|
| 방향·목적 (무엇을 위해, 누가 쓰나, 성공이 무엇인가) | 반드시 확인. "이렇게 이해했다 + 입력 근거"로 |
| 디테일 (구조·형식·문구) | 묻지 않는다. 초안 + 판단 자료 |
| 되돌리기 어려운 외부 동작 | 실행 직전 확인 |

판단 자료 = 추천안과 이유(입력의 어디서) / 결과를 실제로 바꾸는 대안 / **"이런 경우면 이쪽이 낫다"**(갈리는 조건 —
사람은 저울질보다 자기 상황 알아보기가 쉽다) / 고르면 달라지는 것 / 추천이 기대는 가정. 모아서 한 번에, 답이 없으면 추천안.

## 2. 흔한 답으로 수렴한다

출력은 가장 그럴듯한 답, 곧 누구나 아는 모범 사례 쪽으로 간다. "전문가처럼"이라고 하면 말투만 바뀐다.
그런데 "평범하면 안 된다"고 밀면 외부 근거 없이 새로움을 지어낸다 — 지어낸 틀·근거 없는 수치·입력과 무관한 정교함 (폭주).
- 역할 지시("당신은 ○○ 전문가")는 정확도를 일관되게 올리지 못했다는 결과 — Zheng 외 2023 [인용·미확인]
- 전문가의 빠른 첫 판단은 피드백을 받아 온 경험 덕이다 (Kahneman & Klein 2009, Klein의 상황 인식 기반 의사결정) [인용·미확인].
  모델의 첫 판단은 경험이 아니라 최빈값이므로 그 겉모습을 흉내 내지 않는다.

**지침으로 쓰면** — 전문성은 모델 안에서 만들지 말고 바깥 출처에서 가져와 입력에 대 본다:
- **기준선 먼저**: 누구나 쓸 상식 수준 지침을 따로 적고, 지침에는 그것과의 *차이*만 넣는다. 줄마다 "지워도 똑같이 할까?"
- **출처**: 전문 판단마다 사용자 사례·실패 기록·분야 자료·저장소의 좋은 실례 중 하나를 붙이고, 없으면 `가정:`.
- **판정 가능한 모양**: 기준·문턱값·흔한 조언이 틀리는 경우·규칙끼리 부딪칠 때 우선순위·어겨도 되는 때.
  예: "적절한 비유를 쓴다"(상식) vs "특징 3~5개와 대조해 틀림이 하나라도 있으면 버린다"(글 쓰기 스킬의 "비유" 절).
- **결과를 바꾸는 사례**: 기준선을 넘는 규칙마다 "이 규칙이 있으면 결과가 달라지는 사례 하나". 못 대면 장식이다.
- **상식 초안을 먼저 쓰고 나중에 전문적으로 다듬지 않는다** — §1과 같은 이유로 초안 근처에 머문다. 모으기 → 고르기 → 쓰기.

## 3. 지침을 쓸 때 걸리는 성질

| 성질 | 생기는 문제 | 대응 |
|---|---|---|
| **예시를 과하게 따라 한다** — 길이·단어·주제까지 | 예시가 하나면 모든 결과가 그 예시를 닮는다. 열린 작업에선 탐색 범위가 좁아진다 | 출력 형식에만 예시: "핵심은 ○○, 나머지는 바뀌어도 됨" + 영역이 다른 2개. 열린 작업엔 인터페이스·실물 자료 (§5) |
| **허수아비 ✗는 효과가 없다** | 누가 봐도 나쁜 ✗는 모델이 이미 피한다 | ✗는 모델이 실제로 낼 법한 **무난한 답**으로. 예시는 전형 말고 경계 사례 |
| **강한 말·금지형에 과반응** — "반드시"·대문자는 엉뚱한 곳까지, "X 하지 마"는 X를 떠올리게 | 과적용 또는 반대로 작동 | 해야 할 동작으로 + 이유 한 줄. 강조는 되돌리기 어려운 것에만 (Anthropic 최신 모델 프롬프트 가이드) [인용·미확인] |
| **태도 말은 실행되지 않는다** — "신중하게" | 한 번에 끝까지 쓰는 건 그대로 | 확인할 수 있는 질문·동작으로 ("입력의 어디가 이걸 정하나?") |
| **주의 분산·위치** — 긴 맥락의 중간은 덜 쓰인다 (Liu 외, "Lost in the Middle") [인용·미확인] | 긴 지침 중간의 규칙이 무시된다 | 핵심은 앞. **점진 로딩**: 본문은 목차, 조건부 내용은 하위 파일 + 관찰 가능한 읽기 조건("API가 non-200이면 `references/api-errors.md`" — "필요하면" X), 하위 파일은 본문에서 한 단계로 |
| **자유도 불일치** (Anthropic 스킬 작성 가이드 "degrees of freedom") [인용·미확인] | 판단 일을 절차로 묶으면 경직, 순서가 중요한 일을 느슨하게 두면 틀림 | 깨지기 쉬운 순서일수록 정확한 명령·스크립트, 판단일수록 기준과 이유 |
| **기계적 작업에 약하다** — 세기·형식 검사·대조 | "줄 수를 확인하라"가 어림짐작이 된다 | 기계적 단계는 스크립트로. 말로 시키지 않는다 |
| **이유 없는 규칙은 넓혀 쓰지 못한다** | 비슷한 다른 상황에서 규칙이 안 걸린다 | 규칙마다 이유 한 줄 (길게 설득하지 않는다 — 사람용 근거는 따로) |

## 4. 지침이 실행될 때 걸리는 성질

| 성질 | 생기는 문제 | 대응 |
|---|---|---|
| **자기 것을 좋게 평가한다** (Panickssery 외 2024, 자기 선호 편향) [인용·미확인] | 같은 흐름의 자기 검토가 확인 절차로 끝난다 | 실행 결과·미리 적어 둔 기준에 대 본다. 중요하면 새 맥락(별도 에이전트)에서 |
| **사용자에게 맞춘다** (Sharma 외 2023, sycophancy) [인용·미확인] | 가벼운 반박에 근거 없이 판단을 바꾼다. 남의 것 검토가 칭찬 쪽으로 쏠린다 | 새 근거가 있을 때만 바꾼다. 검토 보고는 문제부터 |
| **했다고 하고 확인하지 않는다** | 완료 보고와 실제가 다르다 | 단계마다 관찰 가능한 완료 증거 (파일·명령 출력·스크린샷) |
| **경험이 쌓이지 않는다** — 세션이 끝나면 겪은 실패가 사라진다. 직관은 피드백을 받아 온 경험이 있을 때만 믿을 만하다 (Kahneman & Klein 2009) [인용·미확인] | 같은 실패를 반복하고, 지침은 처음 쓴 상식 수준에 머문다 | 실패·결정을 기록하고 규칙으로 돌리는 고리 (스킬은 `NOTES.md` — `skill-craft/guides/history.md`) |
| **비용 감각이 없다** — 멈출 이유가 주어지지 않으면 계속한다 | 상한 없는 재시도·병렬·서브에이전트·전체 읽기 | 횟수·개수 상한과 멈출 조건. 상한에 닿으면 멈추고 보고. 유료 호출은 기본 꺼짐 |
| **맥락은 사라진다** — 긴 세션은 요약되며 빠진다 | 초반의 범위 표·`가정:` 목록이 사라져 대 볼 대상이 없어진다 | 중간 판단은 파일로 남긴다 (§1의 "입력에 다시 대 보기"가 가능해지는 조건) |
| **지식에 날짜가 있다** | 도구·API·버전을 기억으로 적으면 낡는다 | 바뀌는 사실은 "어디서 확인하라"로, 적을 때는 날짜·출처 |
| **같은 입력에도 흔들린다** — 위 논문에서 잘될 때와 안될 때 차이가 한 번에 줄 때보다 2배 넘게 큼 [인용·미확인] | 판단 단계의 품질이 실행마다 다르다 | 판단 기준을 명시해 흔들림을 줄인다. 중요한 판단은 여러 번 내고 비교 |

## 5. Claude 5세대에서 달라진 것
출처: 다른 프로젝트의 메모 "Claude 5세대 스킬 작성" (공개본에는 없음)
(2026-11-18 웹 조사, 1차 출처 목록은 그 파일) [인용·미확인]
- 과잉 제약·충돌하는 지시가 손실의 원인: Claude Code 시스템 프롬프트를 80% 넘게 지워도 Opus 5·Fable 5 코딩 평가 손실이 없었다고 함.
  → 줄마다 "이 지시가 없으면 틀리나?" (§2 기준선과 같은 질문)
- 실제 실패에서 나온 함정 줄이 가장 값지다. 모델이 스스로 만든 스킬은 효과가 없다는 보고 (SkillsBench, Claude 4.5 세대에서 잰 값)
- 예시는 출력 형식엔 유효하지만 열린 작업에선 탐색 범위를 좁힌다 → 인터페이스(선택지·파라미터)와 실물 참고자료
- 단계 강제보다 목표와 제약. "다시 확인하라"는 Opus 5부터 중복 (스스로 검증)
- Opus 5.5는 거르는 지시를 문자 그대로 따른다 → 검토는 전부 찾게 한 뒤 다음 단계에서 거른다
- 반드시 지킬 규칙은 문장이 아니라 hook으로. MUST·CRITICAL 강조는 과잉 발동
- 압축 뒤에는 앞 5,000토큰만 남음 → 중요한 것은 맨 위. 설명 목록은 항목당 1,536자에서 잘리고 스킬끼리 예산을 나눔
- description은 강하게 밀지 말고 다루는 상황을 넓게 나열. (`when_to_use` 필드는 메모와 설치된 plugin-dev 문서가 엇갈림 — 쓰지 않음)

## 6. 품질 확인
- 어려운 실제 사례 하나를 **지침 있이 / 없이** 돌려 비교한다. 비슷하면 그 지침은 상식에 수렴한 것이다.
- 검토는 쓴 사람의 생각이 아니라 **파일 글자와 실행 결과**에 대 본다 (§4 자기 선호).
