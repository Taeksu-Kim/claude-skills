# 3. 비평 (critique) — 기존 화면 UX 평가

**읽는 때**: 기존 화면 개선 요청. **다 하면**: 사용자가 고른 범위 → 구조 문제면 `2-build.md`, 다듬기면 `4-refine.md`.
목표: 화면을 실제로 보고, 증거와 우선순위 붙은 문제 목록을 낸 뒤, **무엇을 고칠지 사용자에게 묻는다**.
비평 단계에서는 코드를 고치지 않는다.

## 진행

1. **대상 확정** — 어떤 화면·흐름인지, 핵심 과업, 화면 종류(도구·읽기·소개·작품, `1-shape.md` B)를 한 줄로.
   종류별 기대가 다르다: 도구형은 익숙함·밀도·일관성, 소개형은 첫 화면의 제안과 행동 하나.
2. **실제 화면 보기** — `6-verify.md` 대로 띄워 스크린샷(390·1280 폭, 다크모드 포함)을 직접 본다. 핵심 과업을
   실제로 눌러 본다. 코드만 읽은 비평은 첫 줄에 `⚠️ 화면 확인 못 함: <이유>` 를 붙인다.
3. **평가** — 먼저 `../topics/value-density.md` 로 가치·밀도 점검 (핵심 가치 문장이 없으면 추정해 표시), 그다음 아래 A~D.
4. **보고** — 아래 형식. 마지막 줄은 사용자에게 고칠 범위를 묻는 질문 (질문 뒤에 다른 내용을 쓰지 않는다).

## A. 닐슨 10 휴리스틱 — 항목마다 걸린 지점과 증거

| # | 휴리스틱 | 무엇을 보나 |
|---|---|---|
| 1 | 시스템 상태 보이기 | 로딩 표시, 저장·삭제 확인, 진행 단계, 현재 위치, 입력 즉시 검증 |
| 2 | 현실 세계와 일치 | 사용자의 말(전문용어·내부 코드명 X), 익숙한 순서와 단위 |
| 3 | 사용자 통제·자유 | 취소·되돌리기, 빠져나갈 길, 실수 복구 |
| 4 | 일관성·표준 | 같은 동작 = 같은 모양, 플랫폼 관습 |
| 5 | 오류 예방 | 위험한 동작 확인, 잘못된 입력을 애초에 막기, 기본값 |
| 6 | 기억보다 인식 | 선택지가 보임, 이전 화면 정보를 외울 필요 없음 |
| 7 | 유연성·효율 | 숙련자 지름길, 일괄 처리, 필터·정렬 유지 |
| 8 | 미니멀한 디자인 | 핵심만, 시각적 위계 분명 |
| 9 | 오류 인식·복구 | 무엇이 잘못됐고 어떻게 고치는지 사람 말로 |
| 10 | 도움말 | 필요한 곳에 짧고 과업 중심 |

항목마다 `걸림` / `문제 없음` / `해당 없음(이유)` 중 하나, 걸렸으면 **어느 요소에서 무엇이** (스크린샷·요소 이름).
점수·합계·비율 판정은 쓰지 않는다 — 숫자 척도는 중간값으로 몰리고, 사용자가 쓰지 않기로 했다 (D1).
소개형·작품형에서는 7(유연성)·10(도움말)을 `해당 없음`으로 둘 수 있다.
8(미니멀)은 브리프에서 정한 밀도로 본다: 일부러 촘촘하게 정한 도구형 화면은 촘촘함 자체를 걸지 않고,
주 요소가 묻히는지만 본다 (D6).

## B. 인지 부하 체크 — 걸린 항목과 그 요소를 적는다

- 핵심 과업을 방해 요소 없이 할 수 있나
- 정보가 소화 가능한 묶음(묶음당 ≤4)인가 / 관련 항목이 시각적으로 묶였나
- 가장 중요한 것이 즉시 보이나 (주 1개, 보조 2~3개, 나머지는 흐리게)
- 한 번에 한 결정씩인가 / 결정 지점의 선택지가 ≤4개인가 (5~7 경계, 8+ 과부하)
  — 위 수치(묶음당 ≤4·선택지 ≤4)는 브리프 밀도 기준으로 읽는다: 일부러 촘촘하게 정한 도구형 화면이면 개수가 아니라
  "주 요소가 묻히는가"만 본다 (D6과 같은 처리, D11)
- 앞 화면 정보를 기억해야 지금 화면에서 행동할 수 있나 (그러면 실패)
- 복잡함이 필요할 때만 드러나나 (점진적 노출)

흔한 위반: 선택지 벽 · 기억 다리(1단계 정보를 3단계에서 요구) · 숨은 내비게이션 · 전문용어 장벽 ·
모든 요소가 같은 무게 · 같은 동작이 곳마다 다름 · 읽기+결정+이동 동시 요구 · 한 결정에 여러 화면 왕복.

## C. 페르소나 걸어보기

화면 종류에 맞는 2~3명을 골라, 각자 **핵심 과업을 실제로 해보며** 걸린 지점을 구체적으로 적는다
(일반론 금지 — 어느 요소에서 무엇이 막혔는지). 실제로 해 볼 수 없는 것(화면 낭독기 등)은 `(코드로 추정)`으로 표시한다 —
그럴듯한 걷기 결과를 지어내지 않는다. 키보드는 실제로 Tab으로 해 본다 (`6-verify.md` 키보드·DETAIL_JS).

| 페르소나 | 특징 | 걸리는 지점 |
|---|---|---|
| **급한 숙련자** | 안내 건너뜀, 단축키·일괄 처리 찾음 | 불필요한 단계, 일괄 처리 없음, 느림, 강제 안내 |
| **처음 쓰는 사람** | 용어 모름, 다음 할 일을 화면에서 찾음 | 아이콘만 있는 메뉴, 전문용어 에러, 빈 화면에 안내 없음 |
| **접근성 의존 사용자** | 키보드만, 화면 낭독기, 확대 | 포커스 안 보임, 라벨 없는 버튼, 색으로만 구분 |
| **일부러 깨보는 사람** | 0건·1000건·긴 문자열·새로고침·뒤로가기 | 조용히 실패, 새로고침 시 입력 유실, 깨진 빈 상태, `null`·`NaN` 노출 |
| **산만한 모바일 사용자** | 한 손, 자주 끊김, 좁은 화면 | 작은 터치 영역, 가로 스크롤, 끊긴 뒤 상태 유실 |

선택 기준: 대시보드·분석 → 숙련자 + 접근성 · 입력·마법사 → 처음 + 접근성 + 모바일 ·
소개·랜딩 → 처음 + 깨보는 사람 + 모바일 · 데이터 가져오기·편집 → 깨보는 사람 필수 추가.

## D. 이 제품다운가

이 화면이 이 제품을 위해 만들어졌나, 아니면 아무 제품에나 그대로 쓸 수 있는 템플릿인가. 한두 문장.

## 보고 형식

1. **총평** — 잘 된 것, 안 된 것, 가장 큰 기회 하나 (3줄 이내)
2. **휴리스틱 표** — 항목별 걸림 / 문제 없음 / 해당 없음 + 걸린 지점
3. **잘 된 점 2~3개** — 왜 잘 됐는지 구체적으로
4. **우선 문제 3~5개** — 각각 `[P0~P3] 무엇 / 왜 문제 / 어떻게 고칠지(구체적으로)`
   - P0 막힘(과업 불가, 즉시) · P1 큼(혼란·어려움, 다음 작업 전) · P2 작음(우회 가능) · P3 다듬기
   - 애매하면: "사용자가 이것 때문에 물어보러 올까?" → 그렇다면 최소 P1
5. **인지 부하** — 걸린 항목 목록
6. **페르소나별 걸린 지점**
7. **사소한 관찰** (짧게)
8. **질문** — 추천 범위를 이유와 함께 한 줄로 먼저 (예: "P0 2건과 P1 중 필터 위치만 — 나머지 P1은 구조를 바꿔야 해서
   따로"), 그다음 고칠 범위를 묻고 끝낸다
