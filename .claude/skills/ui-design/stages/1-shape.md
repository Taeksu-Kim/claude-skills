# 1. 설계 (shape) — 코드 전에

**읽는 때**: 새 화면·새 기능·새 페이지. **다 하면**: 사용자 확인 → `2-build.md`.
이 단계는 코드를 쓰지 않는다.

## A. 짧은 인터뷰

- **기본은 한 번만 멈춘다**: 1라운드의 답을 저장소(설계 문서·CLAUDE.md·README)에서 먼저 찾아 "이렇게 이해했다 + 근거"로
  C의 브리프 초안에 넣고, 브리프 확인 한 번으로 묻는다 (D11). 저장소에 단서가 전혀 없는 새 프로젝트일 때만 먼저 질문
  **2~3개**를 묻고 기다린다 (AskUserQuestion 이 있으면 사용).
- 설문지를 쏟지 않는다. 정해진 것은 다시 묻지 않고, 뻔한 것은 "이렇게 이해했는데 맞나요?"로.
- 요청이 이미 구체적이면 (설계 문서가 있거나 무엇·누가·어떤 상태가 다 나옴) 인터뷰 없이 C의 3~5줄 브리프 확인만.

**1라운드 — 목적·사람·결과** (결과를 가장 크게 바꾸는 것만)
- 무엇을 위한 화면인가, 어떤 문제를 푸나?
- 누가, 어떤 상황·마음 상태로 오나? (월말에 훑어보러 / 급하게 한 건 고치러 / 처음 알아보러)
- 들어와서 가장 먼저 알아야 하거나 해야 하는 **한 가지**는? 성공하면 어떤 모습?

**레퍼런스 — 그리기 전에 본다** (디자이너가 먼저 하는 일), 역할을 나눠서 — 수준·일관성·기능:
- **수준** — `../topics/craft.md` §1의 레퍼런스 중 미감이 다른 2개를 1440 폭으로 실제로 열어 캡처하고, §2를 읽는다. 모양·컨셉을 베끼지
  않고 요소(아이콘 체계·면·위계·밀도)를 본다. 저장소 안 화면은 같은 스킬로 만든 것이라 수준 기준이 못 된다 (F1).
- **일관성** — 이 저장소에 같은 종류의 화면이 있으면 연다 (`grep -l` 로 다른 프로젝트의 `static/index.html`·README의 화면 절). 용어·동작을 맞춘다.
- **기능 (필수 요소)** — 과업이 이 저장소에 처음인 화면이면(예: 처음 만드는 식단 기록), 같은 과업을 하는 제품 2~3개를 실제로 열어
  (페이지 6개 이내) **갖춰야 할 요소를 기능으로만** 목록으로 적는다 — "최근 먹은 것을 한 번에 다시 추가" ○ / "상단 칩 줄" ✗ (모양을 적으면
  모양이 따라온다). 2곳 이상에 공통인 것만 "기본 기능", 한 곳에만 있는 것은 후보. 이 제품들은 디자인 수준 기준이 아니다 — 측정·나란히 보기를
  하지 않고, 시안을 만들 때는 캡처를 다시 열지 않고 목록만 가져간다. 기능은 먼저 갖추고 디자인은 이 서비스대로 푼다 (사용자 방향 2026-11-20:
  "디자인은 개별적으로, 기본 기능은 우선 갖춘다"). 흐름이 이미 정해진 재디자인에서는 건너뛴다.
브리프 3에 "수준은 어느 레퍼런스의 무엇에서 / 이 서비스만의 것은 무엇" 한 줄, 필수 요소 목록이 있으면 요소마다 "우리 화면에서 어떻게 풀었나"
(일부러 넣지 않는 것은 이유) — 이 대응표가 기본 기능을 다 갖췄는지의 검수다.

**재료·동작·경계 — 묻기 전에 저장소에서 읽는다** (DB·샘플 데이터, 기존 API·라우트, 서버 설정, 프로젝트 `CLAUDE.md`)
- 실제 데이터와 범위 (최소·보통·최대, 이름 길이) / 중요한 상태 (첫 사용·로딩·빈 결과·에러·권한)
- 제약: 로컬 전용, 기존 API, 모바일 사용 여부
- 읽어도 못 정한 것은 묻지 말고 브리프에 `가정:`으로 적는다 — 브리프 확인 때 사용자가 같이 본다 (D3).

**2라운드** (큰 빈칸이 있을 때만) — 결과를 크게 바꾸는데 저장소로는 알 수 없는 것만:
완성도 (탐색용 시안 / 실사용 / 전체 흐름), 손대면 안 되는 것, "겉은 좋아도 틀렸다"고 느낄 결과.

CSS 값이나 "모던/미니멀 중 뭐가 좋아요?" 같은 스타일 메뉴는 묻지 않는다 (방향은 B에서).

## B. 화면 종류 결정 → 해당 파일 하나만 읽는다

방문자가 **성공한 모습**으로 고른다. 제품이 아니라 그 화면 기준 (도구의 소개 페이지는 소개형).

| 종류 | 성공 = | 예 | 읽을 것 |
|---|---|---|---|
| **도구형** | 과업을 끝냄 | 대시보드, 관리·설정, 표, 입력·편집, 분석 화면 | `../modes/operate.md` |
| **읽기형** | 내용을 이해함 | 문서, 가이드, 리포트 웹페이지, 변경 내역 | `../modes/read.md` |
| **소개형** | 결정하고 행동함 | 랜딩, 서비스 소개, 가입·신청 유도 | `../modes/persuade.md` |
| **작품형** | 작품 안에 머묾 | 포트폴리오, 갤러리, 쇼케이스 | `../modes/persuade.md` 의 "작품형" 절 |

**에이전트의 제품 화면이면** (에이전트·컴포넌트를 사람이 브라우저에서 쓰는 화면) 위 종류에 더해
프로젝트에 에이전트 제품 화면 규약 문서가 있으면 그것을 읽고, 브리프에 적는다:
다루는 대상(문서·목차·자료)이 중심 / 사람 개입 동작(편집·다시 생성·선택) / A2A 로 들어온 일이 목록에 어떻게 보이나 /
**채팅이 있는지** — 있으면 세션 2종(Claude Code·로컬 LLM) 선택 자리, 없으면 해당 없음(채팅을 새로 붙이지 않는다).

**시각 방향**:
- 기존 화면·디자인이 있으면 → 그것을 따른다. 방향 문서 읽지 않는다. 단 **재디자인이면** 내용·용어·동작과 사용자가 정한 결정만 지키고
  시각 체계는 새로 정한다 (SKILL §2).
- 없고 도구형·읽기형이면 → 모드 파일의 기본값이 방향이다. 수준은 기본값으로 채워지지 않는다 — `../topics/craft.md` §2로 정한다
  (기본값으로 둔 화면이 아이콘 0·상자 23·굵기 5종으로 나왔다, F1). 사용자가 원하면 `../topics/direction.md`.
- 색을 새로 정하거나 사용자가 색 조합에 불만이면 → `../topics/color.md` (대표색 hex가 아니라 단계·역할·실제 화면 비교로, D18).
- 없고 소개형·작품형이면 → `../topics/direction.md` 로 후보 2~3개를 만들어 사용자에게 고르게 한다.

## C. 브리프

과업이 정해져 있으면 **3~5줄**, 모호하거나 여러 화면이면 아래 전체.
**어느 경우든 맨 위 두 줄은 반드시** (인터뷰를 건너뛴 경우에도):
- **핵심 가치 한 문장** — 이 화면을 쓰면 무엇을 얻나 (예: "카드 3장 중 무엇을 고를지 바로 판단한다")
- **주인공과 밀도** — 그 가치를 보여주는 화면 요소 1~2개, 정보 밀도(촘촘 / 보통 / 여유)와 이유
이 두 줄은 내가 정하지 않고 사용자에게 확인받는다 (재디자인 경로는 멈추지 않고 `가정:`으로 적어 시안과 함께 낸다). 구현 후 `../topics/value-density.md` 점검의 기준이 된다.

**배치안 — 새 화면이면 같은 확인에 붙인다 (질문 횟수는 늘리지 않는다, D8)**: 디자이너는 안을 여러 개 펼쳐 놓고 고른다 —
첫 안에 고정하지 않으려고. 주인공 영역의 배치안 2~3개를 ASCII로 그려 브리프에 함께 낸다.
- 안끼리는 주인공의 위치·위계가 달라야 한다 (색·장식만 다른 안은 안이 아니다).
- 하나를 추천하고 이유는 핵심 가치·밀도에서, 다른 안마다 "이런 경우면 이쪽이 낫다" 한 줄. 답이 없으면 추천안으로 2-build.
- 눈으로 비교하고 싶다고 하면 Artifact 시안으로 (사용자가 Artifact 시안으로 비교한 기록:
  광고 보고서 프로젝트의 디자인 참고 문서 — 다만 형식별 시안이라 배치 대안 비교는 아니다).
- 작은 수정·부분 다듬기에는 하지 않는다.
- **재디자인이면 ASCII가 아니라 정적 시안 2개**를 만든다: 실제 내용·실제 글꼴·아이콘으로 만든 HTML 한 장씩, 구조가 다른 것(예: 읽기 중심 /
  작업 중심). 1440 폭으로 캡처하고 `../topics/craft.md` §3·§4-1·2(기본값 점검·측정·영역 확대 비교)를 거친 뒤 이미지로 낸다.
  ASCII·단일안으로는 수준 차이가 보이지 않아 v1이 그대로 코드가 됐고, 시안 2개를 만들자 비로소 차이가 보였다 (F1).
  응답을 못 받으면 추천 시안으로 `2-build`를 진행한다.
- **기존 시각 체계가 없는 새 화면**(새 프로젝트)도 추천 배치안 하나를 실제 내용 정적 시안 1장으로 만들어 `../topics/craft.md` §4(측정·영역
  비교·평가자)를 먼저 거친 뒤 `2-build`로 간다 — ASCII만 거쳐 코드로 가면 수준 문제가 마지막 확인에서야 나오고 2회 상한에 걸려 남는다 (F1과 같은 모양).
- 시안(재디자인·새 화면 모두)의 목록·개수·표는 실제 데이터에서 스크립트로 채운다 — 손으로 옮기면 머리 개수("정리됨 7")와 보이는 항목 수(5)가 어긋나고 id가 잘려,
  평가자가 "항목이 사라졌다"를 디자인보다 먼저 짚었다 (D14 검증 1회차). 정렬 기준은 화면에 보이게.


1. 과업과 사용자 — 누가 어떤 맥락에서, 무엇이 필요. **실제로 쓰는 사람**이 주인 본인인지 다른 사람(비개발자 담당자·일반인)인지,
   그 사람이 "도움 없이 과업을 끝냈다"를 무엇으로 알 수 있는지 (결과를 판정하는 쪽, D11)
1-1. 흐름 — 들어옴 → 핵심 과업 → 끝 → 다음에 다시 올 때. 화면 한 장이 아니라 이 흐름에서 이 화면이 맡는 곳 (디자이너는 흐름부터
   설계한다 — 흐름 문제가 첫 구현 뒤에야 나온 기록: 결과 해설 화면 프로젝트·광고 보고서 프로젝트 README의 2차 점검, D11)
2. 결과와 증거 — 핵심 행동, 성공 기준, 화면이 보여줄 실제 데이터
3. 화면 종류와 방향 — B의 결정, (있으면) 고른 방향
4. 범위와 경계 — 완성도, 손대지 않을 것, 비목표
5. 상태와 범위 — 데이터 범위, 필요한 상태들. 데이터는 실제 규모로 늘려 기본으로 몇 건을 보이고 무엇을 접을지 정한다.
   **화면이 판정·요약·경고를 말하면 색·배치 전에 경계표를 먼저**: 0건 / 값 없음(null) / 기준이 0 / 음수 / 비교 대상 없음마다
   "판정할 근거가 있나"와 그때 문구·색·정렬·집계. "0원 썼다"와 "자료가 없다"는 다른 상태이고, "기준 없음 + 값 있음"(예산 0인데
   지출)은 회색으로 숨기지 않는다 (D12 — 빈 달을 "예산 안"으로 축하하고 예산 밖 지출을 회색으로 숨긴 시험 결과).
   만들면서 스스로 덧붙인 경고·자동 표시("구독 반복 결제" 같은)도 표에 넣는다 — "참이 되려면 무엇이 성립해야 하나"를 적고
   반례(섞인 분류의 가맹점 등)를 데이터로 넣어 본다 (D13 — 경계표를 판정 문장에만 적용해 덧붙인 경고가 오탐한 시험 결과).
   막대·눈금이 있으면 **가장 큰 값이 나머지의 수십 배인 데이터**를 넣어 보고 눈금을 정한다 (공통 눈금 / 기준 대비 비율·상한에서 자르고
   넘침 표시) — 큰 결제 하나에 다른 막대가 모두 1~3% 굵기가 돼 비교가 사라진 결과 (D13)
6. 위계와 배치 — 무엇이 먼저 보이나, 영역 구분, 반응형 (CSS가 아니라 의도로). 새 화면이면 위 배치안과 추천
7. 미결정 — 구현자가 임의로 정하면 안 되는 것

브리프를 보여주고 **확인 또는 한 번의 수정**을 받은 뒤 멈춘다. 응답을 받을 수 없는 상황(백그라운드·headless)이면 `가정:`을 붙인 추천안으로 `2-build`를 진행하고, 보고 맨 앞에 가정 목록을 둔다 (D11).
