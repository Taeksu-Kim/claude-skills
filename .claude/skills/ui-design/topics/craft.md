# 전문가 수준 — 레퍼런스 · 시각 체계 · AI 기본값 · 수준 비교

**읽는 때**: 새 화면·재디자인에서 그리기 전(`../stages/1-shape.md`, §1·§2), 구현할 때(`../stages/2-build.md`, §2·§3),
확인할 때(`../stages/6-verify.md`, §3·§4). 작은 수정·부분 다듬기에는 읽지 않는다.
**왜 있나 (F1)**: 기술 점검(넘침·대비·글자 단계)을 다 통과한 화면이 "단순·투박·AI 티"로 판정됐다. 준수 검사는 바닥만 막고
수준은 올리지 못한다. 이 파일은 **닿아야 할 수준**을 레퍼런스에서 가져온다 — 모양을 베끼는 게 아니라 요소를 본다.
컨셉·구성·색은 그 서비스에 맞춰 따로 정한다 (사용자: "전문 디자인으로서 좋은 걸 보고, 컨셉은 그때그때 맞추고").

## 1. 레퍼런스 — 수준을 보는 곳 (확인 2026-11-20, 사이트가 바뀌면 다시 본다)

갖춰야 할 기능은 여기가 아니라 `../stages/1-shape.md`의 "기능" 레퍼런스에서 — 같은 과업 제품은 기능 목록용이고 수준 기준이 아니다.

고르는 기준: ① 디자인 품질 근거가 바깥에 있다 (업계가 꼽는 디자인팀·디자인상·큐레이션) ② 실제 제품의 실제 화면 (연출·부품 데모·가짜
데이터 X) ③ 밝은 테마, 한국어 하나 이상 ④ 미감이 다른 것 2~3개. **"열린다"·"비슷한 서비스다"는 고른 이유가 아니다** —
접근 쉬운 부품 데모(shadcn)와 과업만 같은 서비스를 골랐다가 기준이 틀어졌다 (F1 레퍼런스 검토).
AI 화면 생성기의 기본 스타일(shadcn 기본 등)은 기준이 아니라 "흔한 수준" 예시다.

화면은 1440 폭으로 직접 열어 캡처한다 (기억으로 판단하지 않는다). 레퍼런스 캡처는 그 작업의 기록 폴더에만 두고 스킬에는 넣지 않는다
(남의 화면, 공개 저장소). 열리지 않으면(봇 확인·로그인·바뀜) 표의 다른 팀으로 하고, 모두 실패하면 보고에 적고 §2만으로 간다.
여기 없는 분야면 같은 기준으로 하나를 더 고르고 이 표에 근거와 함께 한 줄 더한다.

## 2. 시각 체계 — 정하는 순서도 이 순서 (색은 뒤)

각 줄: 흔한 수준 → 닿아야 할 수준 · 근거. **값(px·그림자·글꼴·간격)은 그 팀이 자기 서비스에 고른 예시다 — 처방이 아니다.**
이 서비스에 무엇을 고를지는 줄마다 "우리 화면에서 무엇을 위해"로 정한다. 레퍼런스의 값을 그대로 옮기면 모든 프로젝트가 같은
모양으로 모인다 (새 맥락 검토 2026-11-20, C2). 개수(아이콘·그림자)는 목표가 아니다 — 숫자를 채우려 더하면 장식이 된다.

1. **밀도·점진적 노출** — 모든 정보를 첫 화면에 펼침 → 첫 화면엔 판단에 쓰는 것만, 나머지는 들어가서 보거나 접는다.
   (v1: 첫 화면 글자 2,890 — 레퍼런스 4곳보다 많았다.) Primer Layout: "집중된, 차분한" 화면, 단은 768px 이상 2개·3번째 단은 1400px 이상에서만.
2. **아이콘 체계** — 아이콘 없음, 또는 ✓·▸·↓ 같은 글자 기호 → 한 계열(선 굵기 하나, 크기 2~3단계) 아이콘을 **내비와 행동 버튼에**.
   메타(날짜·링크·수치 라벨)·태그 칩·라벨 앞에는 붙이지 않는다 — 글자가 이미 말하는 것을 반복하는 장식이고, 평가자가 "라벨마다 아이콘
   하나 = AI 기본 패턴"으로 짚었다 (D17: 메타마다 붙였다가 걸림). 상태 아이콘은 여러 상태가 한 목록에 섞여 보일 때만 (빈 원·채운 원·체크). 장식 아이콘은 `aria-hidden`, 버튼 안 단독 아이콘은 이름을 단다 (Primer Icons).
   아이콘마다 "없으면 무엇을 못 알아보나"에 답이 있어야 남긴다 — 답이 없는 아이콘은 장식이다. (v1: 아이콘 0.)
3. **면과 고도** — 모든 묶음을 4면 1px 상자로 → 고도를 세 방법으로 나눠 쓴다: 바탕 톤(회색 바닥 위 흰 면) · 그림자(떠 있는 몇 안 되는
   것에만, 아주 옅게 — SEED s1 `0 1px 4px rgba(0,0,0,.08)`) · 선(한 면 구분선, 목록은 들여쓴 구분선 또는 없음 — TDS ListRow).
   그림자는 "실제로 떠 있는 것"에만 — 떠 있지 않은 카드에 더하지 않는다. 문제는 개수가 아니라 "모든 묶음이 같은 상자"다. (v1: 그림자 1.)
4. **글자 위계** — 크기를 그때그때, 700·800 반복 → 역할 이름 붙인 글자 스타일(화면 제목·본문·라벨·메타·숫자)을 한 번 정의 (SEED
   시맨틱 텍스트 스타일, TDS "큰 제목·일반 본문"). 굵기 3~4종, 800 쓰지 않음. 강조를 색으로 하지 않는다 (Primer Typography).
   (v1: 굵기 5종에 800, 가장 많이 쓴 글자 12px.)
5. **회색 단계와 색 역할** — 링크·라벨·강조를 모두 브랜드색 글자로 → 회색을 역할로 나눈다: 바탕·면 / 구분선 / 보조 글자·아이콘 /
   본문 (Primer 중립 단계: 바탕 0~5, 선 7~8, 글자·아이콘 9~10). 색은 역할마다 한 뜻 (Primer: accent = 링크·선택·포커스, success = 주 버튼…)
   — 한 색이 두 뜻을 갖지 않는다. 색 글자 수 자체는 기준이 아니다 ([측정] GitHub 19·Stripe 34는 링크).
   색을 만드는 법(단계·역할·후보 축)은 `color.md` — 설계·구현 단계 표에서 연다.
6. **줄간격 둘로** — 화면 전체 한 값 → 화면 글자(버튼·목록·메타) 1.35~1.5, 제목은 더 좁게, 한국어 긴 글 1.7~2.0.
   TDS 본문 17/25.5·15/22.5(1.5), 제목 22/31·30/40, 브런치 한국어 본문 2.0 (예시). (v1: 1.6 일괄.)
7. **간격은 관계로** — 4px 단계만 지킴 → 단계 위에 관계 이름을 붙인다: 글자 사이 · 칩 사이 · 부품 사이 · 화면 가장자리 (SEED: 6·8·12·16px).
   같은 관계는 화면 어디서나 같은 값.
8. **글꼴** — 손대지 않음 → 이 서비스에 맞게 고른다 (Windows의 맑은 고딕은 의도와 어긋나는 경우가 많다 — SEED가 Windows에서만
   Pretendard를 쓰는 이유. 한 예일 뿐 정답 글꼴이 아니다). 숫자는 `tabular-nums`. 로컬 앱(127.0.0.1)은 글꼴 파일을 `static/` 안에 두거나, CDN이면 끊겼을 때 시스템 글꼴로
   떨어져도 깨지지 않게 한다 — 인터넷 없이도 뜨는 것이 로컬 도구의 약속이다. 효과는 1~7보다 작다 (시스템 글꼴로도 잘 만든 화면이 있다).
9. **시그니처는 한 곳** — 브랜드 요소를 문단·카드·로고에 모두 → 그 제품의 핵심 동작 하나에만. 나머지는 조용히 (frontend-design
   "대담함은 한 곳에").

10. **컨트롤 모양은 하는 일로** — 상태 바꾸기·보기 전환·행동·태그·수치가 같은 테두리 버튼이나 같은 회색 알약 → 하는 일마다 모양이
   다르다: 행동 = 버튼(주 동작 하나만 채움) / 보기 전환 = 내용 위의 탭 / 대상의 상태 = 그 대상 옆의 상태 표시 + 바꾸는 메뉴 /
   태그 = 하나씩 누를 수 있는 칩 / 수치 = 라벨 + 숫자 카운터(누를 수 없으면 칩 모양을 쓰지 않는다). 한 컨트롤은 한 가지만 고른다
   (세션 종류와 대화 목록을 select 하나에 넣지 않는다). 근거: 평가자 실패 장면 — 두 화면 모두 상태 분할 컨트롤이 "보기 전환 탭"으로
   읽히고, 태그와 수치가 같은 알약이라 무엇을 누를 수 있는지 모름 (D14 검증 1회차). GitHub "Fork 43.9k" 카운터, Primer StateLabel.

## 3. AI 기본값 점검 — 도구·읽기형 포함 (시안을 보이기 전, 구현 뒤)

이유 없이 나왔으면 선택이 아니라 기본값이다. 사용자가 원한 것이면 그대로 둔다. 하나라도 걸리면 그 부분에 "비슷한 다른 요청에서도
똑같이 나올 답인가?"를 묻고, 그렇다면 고치고 무엇을 왜 바꿨는지 보고에 적는다.
- `direction.md` §3의 1~3 (크림 바탕 + 세리프 제목, 검은 바탕 + 형광 강조 하나, 신문 레이아웃) — 도구·읽기형에서도 똑같이 기본값이다
  (논문 분석 프로젝트 v3가 크림 `#f3f2ec` + 세리프 제목으로 1번에 걸렸는데 이 목록에 없어 놓쳤다, D18)
- 똑같은 둥근 카드에 같은 그림자, 위계와 상관없이 모서리 하나 · 장식용 그라데이션 (frontend-design)
- 제목마다 자간 벌린 대문자 라벨 · 메타를 가운뎃점으로 잇기(`A · B · C`) · 버튼·링크 끝 `→` · 작은 데이터 라벨에 고정폭 글꼴 ·
  순서가 아닌데 번호(01/02) (frontend-design. v1에 실제로 나옴: `태그 … · 연결 2 · 쓰인 곳 5`, 고정폭 라벨 8개)
- 색 띠 헤더 + 흰 알약 탭 (셸 색 자체는 문제가 아니다 — 프로젝트가 셸에 주 색을 정했으면 따르고, 띠 + 알약이라는 모양을 기본값으로 고르지 않는다) · 모든 묶음을 테두리 상자로 · 아이콘 대신 글자 기호 · 시그니처를 모든 곳에 · 700~800 굵게 반복 ·
  줄간격 한 값 (v1에서 실제로 나옴, F1)

## 4. 수준 비교 — 확인 단계에서 (새 화면·재디자인, 생략 금지)

Read로 여는 이미지는 긴 변이 약 1,568px을 넘으면 줄어든다 (Anthropic Vision 문서 — Claude Code Read도 같은지는 확인 안 함). 1440 화면
두 장을 한 장에 붙이면 각 화면이 절반 크기라 아이콘 선 굵기·1px 선·굵기 차이·여백이 안 보인다. 그래서 **전체 캡처는 구성만**, 디테일은 영역으로 본다.
1. **측정 (우리 화면만)**: `CRAFT_JS`로 잰다. 아이콘 0 / 굵기 5종 이상 또는 800 / 그림자 0 / 첫 화면 글자 2,500 이상은 v1과 같은 실패 모양이니
   §2의 그 줄을 다시 본다. 레퍼런스 값과 나란히 놓고 맞추지 않는다 — 반대로 아이콘·그림자를 늘려 숫자를 채우는 것도 같은 실패다.
   `mainSize`는 가장 많이 쓴 크기라 여러 칸 화면에서는 메타 크기가 잡힌다 — `sizes`와 함께 읽는다.
2. **영역 확대 보기**: `device_scale_factor=2` 컨텍스트에서 `screenshot(clip=…)`으로 같은 역할의 영역(머리·툴바 / 목록 행 2~3개 /
   주 행동 / 입력창)을 잘라, 우리 것과 §1 레퍼런스의 같은 역할 영역을 위아래로 붙인다 (이미지 긴 변 1,568 이하). 영역마다 높이·안쪽 여백·
   글자 크기와 굵기·아이콘 크기와 선 굵기·정렬선을 적어 비교한다. 다듬는 중에는 이 영역 캡처를 자주 찍어도 된다 (전체 캡처보다 싸다).
3. **고른 시안과 대조 (재디자인 구현 뒤)**: 사용자가 고른 시안과 구현을 2와 같은 영역으로 잘라 나란히 놓고 차이를 목록으로 — 의도한 차이는
   이유를 적는다. 영역 단위로 기존 코드를 고치다 옛 화면 쪽으로 되돌아가는 것을 잡는다.
4. **새 맥락 평가자 1명** (서브에이전트를 쓸 수 있을 때). 브리프는 주지 않는다. 전체 캡처 1장과 2의 영역 이미지를 주고 이 순서로 묻는다 —
   ① 이 화면이 무엇을 판단하거나 하게 하는 화면인지 한 문장 ② 가장 먼저 눈이 간 곳 세 개를 순서대로 (①②를 브리프 핵심 가치 문장과 대조한다 —
   만든 사람은 답을 알아서 5초 테스트가 후하다) ③ 이런 화면이면 당연히 있어야 할 기능 중 빠진 것 ④ 레퍼런스와 같은 급인가,
   아마추어처럼 보이는 곳 (위치마다) ⑤ §3 목록에 걸리는 곳,
   뜻 없이 붙은 아이콘·그림자 ⑥ 특정 제품을 베낀 것처럼 보이나. 이 스킬로 만든 **다른 프로젝트 화면**이 있으면 1장 함께 주고
   "같은 템플릿에서 나온 것처럼 보이나"도 묻는다. 만든 사람의 판정과 다르면 평가자 쪽을 따라 고친다. 쓸 수 없으면 보고에 "자기 평가만 함".
   **회차 상한 (D4·D16)**: 평가자에게 다시 보이는 가치·구조 회차는 2회까지. 디테일 다듬기(2의 영역 비교로 "레퍼런스와 다른 점" 목록을 만들고
   고치기)는 5회까지 — 이유 없는 차이가 0이면 그 전에 멈추고, 5회 뒤 남은 차이는 보고에 낸다.

